# 后端研发项目管理办法

> **适用范围**：前端由外部厂商负责、后端由我方负责的协作项目\
> **版本**：v1.0\
> **发布日期**：2026-04-30\
> **归口部门**：项目管理办公室（PMO）

***

## 第一章 总则

### 第一条 目的

为规范后端研发项目的管理流程，明确各参与方的职责与协作要求，保障项目质量与交付效率，特制定本办法。

### 第二条 适用范围

本办法适用于前端由外部厂商负责、后端由我方负责的所有研发项目，包括新项目立项、迭代需求交付及系统改造项目。

### 第三条 管理原则

1. **门禁驱动**：以评审门禁为质量关卡，未通过不得进入下一阶段
2. **增量交付**：开发与联调采用增量迭代模式，降低集成风险
3. **协议先行**：接口协议冻结前不得进入开发阶段
4. **责任到人**：每个环节明确RACI，杜绝责任模糊
5. **闭环管理**：所有问题须有记录、有跟踪、有闭环

### 第四条 术语定义

| 术语      | 定义                              |
| ------- | ------------------------------- |
| RACI    | R=执行者，A=审批/负责者，I=知会者，C=咨询者      |
| 评审门禁    | 阶段性质量检查点，须提交规定交付物并通过审批方可推进      |
| 接口协议冻结  | 接口协议经评审通过后锁定，变更须走变更流程           |
| 增量交付    | 开发过程中将已通过测试的接口分批交付联调            |
| P0/P1缺陷 | P0=阻断性缺陷（系统不可用），P1=严重缺陷（核心功能异常） |

## 第二章 组织与职责

### 第五条 角色与职责

| 角色            | 职责                                   |
| ------------- | ------------------------------------ |
| **项目经理**      | 统筹项目计划与资源协调；审批门禁①②③；监控项目风险与进度；协调跨方问题 |
| **技术负责人**     | 审批技术方案；把控接口设计质量；审批上线Checklist；技术风险决策 |
| **研发负责人**     | 执行接口测试（步骤8a）；提交后端测试报告（门禁③）；接口质量守门    |
| **后端研发组**     | 执行需求分析、接口设计、开发、联调、上线支持；提供Mock数据      |
| **前端厂商**      | 确认接口清单与协议可消费性；参与联调；验收接口对接结果          |
| **产品组**       | 发起需求交底；确认需求覆盖度；执行验收测试                |
| **测试组**       | 执行功能测试与集成测试；参与Demo/生产环境验证            |
| **运维/DevOps** | 执行CI/CD流水线部署；服务健康监控；上线审批与回滚执行        |

## 第三章 需求分析阶段管理

### 第七条 需求交底

1. 产品组发起需求交底会议，须提前提供需求文档/PRD
2. 后端研发组须在会上识别技术风险并记录
3. 交底会议须形成会议纪要，含需求清单、优先级、时间节点
4. 会议纪要须在会后2个工作日内分发至相关方

### 第八条 后端功能分析

1. 后端研发组须将需求拆解为可执行的后端功能点
2. 涉及跨系统交互的功能点须明确调用关系与依赖
3. 须输出后端功能分析文档，含功能点清单、技术方案、风险清单
4. 技术方案须经技术负责人审批

### 第九条 接口拆解

1. 接口清单须与前端厂商对齐，确保前后端理解一致
2. 每个接口须明确：接口名称、请求方式、业务描述、依赖关系
3. 须区分新增接口与复用接口

### 第十条 工作量评估

1. 工时评估须按接口/功能点逐项进行
2. 须预留联调、自测、文档编写时间
3. 须包含10%-15%缓冲时间
4. 复杂接口须单独标注风险

### 第十一条 评审门禁①：接口清单 + 工作量预估

1. **提交物**：接口清单 + 工作量预估
2. **审批人**：产品组（确认需求覆盖度）、项目经理（确认排期合理性）
3. **通过标准**：
   - 接口清单覆盖所有需求功能点
   - 工作量评估无重大遗漏
   - 排期与项目里程碑对齐
4. **未通过处理**：返回后端功能分析步骤重新梳理
5. **特别要求**：接口清单须经前端厂商确认签收

## 第四章 接口设计阶段管理

### 第十二条 接口协议编写

1. 每个接口须编写详细协议文档，含URL、Method、请求参数、响应结构、错误码、示例
2. 须定义公共规范：分页、鉴权、版本号、时间格式
3. **强制要求**：
   - 错误码须统一编码，禁止各接口自定义
   - 枚举值须提供完整字典
   - 金额、时间等字段须明确精度与格式
   - 接口变更须记录变更日志

### 第十三条 接口协议评审

1. 评审须以**现场/线上会议**形式进行，禁止仅文档异步评审
2. 前端厂商须逐接口确认可消费性
3. 测试组须确认接口可测试性
4. 评审记录须有双方签字/确认截图
5. 评审后接口协议冻结，变更须走变更流程

### 第十四条 评审门禁②：接口协议 + 前后端评审

1. **提交物**：接口协议文档 + 前后端评审记录
2. **审批人**：前端厂商（确认接口可消费）、后端技术负责人（确认技术方案）、项目经理（确认无阻塞）
3. **通过标准**：
   - 前后端双方对全部接口达成一致
   - 评审问题全部闭环
   - 接口协议版本冻结
4. **未通过处理**：返回接口协议编写步骤修改后重新评审
5. **特别要求**：
   - 评审记录须有双方签字/确认截图
   - 冻结后的接口变更须提交变更申请并重新评审

### 第十五条 接口变更管理

1. 接口协议冻结后，任何变更须提交《接口变更申请》
2. 变更申请须包含：变更原因、影响范围、前后端影响评估
3. 变更须经技术负责人审批、前端厂商确认后方可执行
4. 紧急变更须经项目经理特批，事后补走变更流程

## 第五章 开发与联调阶段管理

### 第十六条 开发规范

1. 须按接口协议编码实现，禁止私自修改已冻结的接口协议
2. 核心逻辑单元测试覆盖率须≥80%
3. 代码提交前须完成自测

### 第十七条 研发负责人接口测试（步骤8a）

1. 研发负责人是接口提交质量的唯一守门人
2. **未通过接口测试的接口不得进入前后端联调**
3. 测试须覆盖：正常流、异常流、边界值
4. 须校验：响应字段完整性、错误码与协议一致性、空值处理、分页参数
5. 发现问题打回开发修复，修复后重新验证
6. 通过测试的接口增量交付给联调环节

### 第十八条 前后端联调（步骤8b）

1. 仅接收8a增量交付的已通过接口测试的接口
2. 联调环境须与接口协议版本一致
3. 联调问题须当日记录、当日修复或给出修复计划
4. 联调发现的阻断性问题反馈给后端研发组持续修复支持

### 第十九条 增量交付与迭代循环

8a与8b形成**增量交付 → 联调 → 反馈修复 → 增量交付**的迭代循环：

1. 8a先行启动，开发数日后将已通过测试的接口增量交付给8b
2. 8b联调中发现的问题反馈给后端研发组修复
3. 修复后的接口重新经8a验证后再次增量交付
4. 两个环节均完成后，方可进入评审门禁③

### 第二十条 评审门禁③：后端测试报告

1. **提交物**：后端测试报告（含接口测试结果、联调结果、缺陷统计、遗留缺陷清单）
2. **提交人**：研发负责人
3. **审批人**：项目经理
4. **通过标准**：
   - 研发负责人接口测试全部通过
   - 前后端联调全部通过
   - 无P0/P1遗留缺陷
   - P2及以下缺陷有明确修复计划
5. **未通过处理**：返回开发步骤，修复缺陷后重新走8a接口测试 + 8b联调
6. **核心意义**：未通过此门禁的代码不得进入测试组

***

## 第六章 测试阶段管理

### 第二十一条 测试组测试

1. 测试组按测试用例执行功能测试与集成测试
2. P0/P1缺陷须在24小时内修复
3. 缺陷须全程跟踪至闭环

### 第二十二条 验收测试

1. 产品组按业务场景验收确认
2. 须确认需求功能点全部覆盖
3. 须确认无P0/P1遗留缺陷
4. 验收不通过须明确不通过原因及整改要求

***

## 第七章 上线发布阶段管理

### 第二十三条 上线Checklist

1. 须整理：环境变量与开关配置、数据库变更脚本（DDL/DML）、依赖服务变更
2. 须提供回滚方案
3. SQL脚本须在测试环境验证过
4. 配置变更须标注影响范围
5. Checklist须逐项核对，禁止遗漏

### 第二十四条 Demo环境发布与验证

1. 通过CI/CD流水线自动化部署至Demo环境
2. 部署失败须立即回滚并排查原因
3. 须按Checklist逐项验证，禁止跳项
4. 验证不通过须修复后重新部署验证
5. 须确认Demo环境与生产环境配置一致性

### 第二十五条 生产环境发布

1. 须获得上线审批
2. 须在约定维护窗口执行
3. 须有回滚预案
4. 须通知相关方上线时间

### 第二十六条 生产环境验证

1. 上线后须持续监控1-2d
2. 须验证核心功能、监控系统指标（错误率、响应时间）
3. 发现阻断问题须立即启动回滚
4. 上线完成须通知产品组、前端厂商、项目经理

***

## 第八章 风险与问题管理

### 第二十七条 风险识别与上报

1. 各阶段发现的风险须及时记录并上报项目经理
2. 技术风险由技术负责人评估并制定应对方案
3. 排期风险由项目经理协调资源或调整计划

### 第二十八条 问题跟踪

1. 所有问题须记录问题清单，含：问题描述、严重等级、责任人、计划修复时间
2. P0/P1问题须在24小时内修复
3. 联调问题须当日记录、当日修复或给出修复计划
4. 问题修复后须经相应验证环节确认闭环

### 第二十九条 门禁回退管理

1. 门禁未通过时，须按回退路径返回对应步骤
2. 回退后须重新完成该步骤及后续所有步骤
3. 回退原因须记录并纳入组织过程资产

***

## 第九章 组织过程资产管理

### 第三十条 经验教训沉淀

1. 每次项目复盘后须增量补充组织过程资产
2. 组织过程资产按编号规则管理：`OPA-YYYY-NNN`
3. 每条资产须包含：问题分类、关联步骤、问题描述、根因分析、改进措施

### 第三十一条 流程改进

1. 项目经理须在项目结束后组织复盘会议
2. 复盘须覆盖：流程执行情况、门禁有效性、协作问题、质量指标
3. 改进建议须经PMO评审后纳入流程修订
